# 직접 검증하기

만든 사람이 아니라 **쓰는 사람의 자리에서** 확인하는 순서. 위에서 아래로 갈수록
느려지고, 대신 실제 제품에 가까워진다. 세 단계 어디서 멈춰도 그 단계까지는 참이다.

숫자는 전부 분자와 분모로 적는다. `0.98` 은 49/50 에서도 490/500 에서도 같게 읽히는데
두 번째가 훨씬 강한 주장이기 때문이다.

---

## 1단계 · 30초 — 키도 VS Code 도 없이

요청 한 줄을 넣고, 읽어낸 것을 눈으로 본다. `--offline` 이면 모델에 아무것도 묻지
않으므로 API Key 가 없어도 된다.

```bash
pnpm install
pnpm design:preview -- --offline --prompt "로그인 오류를 고쳐줘"
```

**무엇을 보면 되는가.** "요구사항"과 "검증 방법"이 요청에서 나온 말로 쓰여 있는지.
지어낸 낱말이 하나라도 있으면 그것이 결함이다.

이어서 아래 네 문장을 넣어 보면, 최근에 고친 것들이 각각 보인다.

| 넣어 볼 문장 | 확인할 것 |
|---|---|
| `후보 솔루션을 비교해 주세요. 다만 특정 벤더의 제품명은 결론에 넣지 말아 주세요.` | "하지 않을 작업"에 금지가 서고, "검증 방법" 1번이 그 금지를 그대로 검사한다 |
| `API Key는 SecretStorage에만 저장하고 설정 파일에는 쓰지 마.` | 위와 **반대로** 결과물 금지가 서지 않는다 — 이건 파일에 쓰지 말라는 것이라 도구 관문이 맡는다 |
| `테스트를 실행하지 말고 코드만 보여줘.` | 실행 금지가 서고, 검증이 `run_command` 를 막는다 |
| `알아서 다 해줘.` | 요구사항이 **하나도** 나오지 않는다. 읽어낼 것이 없으면 지어내지 않는다 |

내부까지 보고 싶으면 `--advanced` 를 붙인다. 각 시나리오가 실제로 무엇을 검사하는지
(`oracle noOutput[…]`, `oracle forbid[run_command]`) 가 그대로 찍힌다.

```bash
pnpm design:preview -- --offline --advanced --prompt "…"
```

## 2단계 · 5분 — 모델 추천까지

`.env` 에 키를 넣으면 `--offline` 없이 돌릴 수 있고, 그때 비로소 **어느 모델을 왜
추천하는지**가 나온다.

```bash
cp .env.example .env    # HASA_API_KEY 를 채운다. .env 는 커밋되지 않는다
pnpm design:preview -- --prompt "사내 문서 검색 기능을 만들어줘"
```

**무엇을 보면 되는가.** 추천 옆에 점수 분해와 근거 등급이 붙어 있는지. 등급은
`declared`(공급자가 그렇다고 함) < `benchmark`(외부 벤치마크 — 이 하네스에 대해서는
아무 말도 하지 않는다) < `harness_eval`(우리 시나리오로 재봄) < `observed`(실제로
일어남) < `manual` 순이고, 낮은 등급을 높은 척하지 않는 것이 핵심이다.

## 3단계 · 실제 제품 — VS Code 확장

```bash
pnpm build:extension
```

VS Code 에서 이 폴더를 열고 `F5`. 새 창에서 `Ctrl+Shift+P` →
**`HASA: 하네스 설계 (요구사항 → 모델 추천)`**.

패널에서 확인할 것:

- 요구사항 줄마다 **`요청` / `추정` / `금지` / `기본`** 태그가 붙는다. `요청` 은
  사용자가 쓴 말에서 나온 것, `추정` 은 런타임이 읽은 것, `기본` 은 하네스 자신의
  조건이다. 이 넷이 섞여 있으면 안 된다.
- 요구사항을 읽은 것이 **모델인지 런타임인지**가 화면에 적혀 있다.
- 부를 수 있는 모델이 없을 때, 왜 없는지(키가 없는지 · 권한이 없는지 · 목록이
  비었는지)를 구분해서 말한다.
- **코딩 에이전트로 넘기기** 를 눌러도 아직 아무것도 보내지 않는다. 정해지지 않은
  것이 남아 있으면 그것부터 보여준다.

설계 단계에서는 **파일이 하나도 바뀌지 않는다.** 이것은 믿어달라는 말이 아니라
`preview.test.ts` 가 `writeFile` 과 `spawn` 을 바꿔치기해서 실제로 확인하는 성질이다.

## 만든 쪽의 주장을 다시 재기

아래는 전부 "테스트가 통과한다"가 아니라 **"테스트가 무언가를 실제로 잡는다"**를
재는 것들이다. 통과하는 테스트와 아무것도 검사하지 않는 테스트는 겉모습이 같다.

```bash
pnpm typecheck        # src + 확장 + 웹뷰
pnpm test             # 전체 (수 분)

pnpm design:anchors   # 변이 치환 문자열이 코드와 어긋나지 않았는지 (몇 초)
pnpm design:answers   # 적어 둔 정답을 하나씩 바꾸고 테스트가 잡는지 (~10분)
pnpm design:mutate    # 방어선을 하나씩 지우고 테스트가 잡는지 (수십 분)
pnpm audit:assertions # 단언을 한 번도 실행하지 않는 시험 블록 (수 분)
```

`design:mutate` 와 `design:answers` 는 소스를 잠깐 고쳤다 되돌린다. **돌아가는 동안
파일을 편집하면 안 된다** — 복원이 편집을 덮어쓴다.

## 무엇이 아직 안 되는지

`goldRequirements.ts` 의 `UNMEASURED` 가 재지 않은 것의 목록이고, 0으로 채우지 않는다.
일부러 읽지 않기로 한 것도 테스트로 고정되어 있다 — `쓰다`(쓰기와 사용하기를 가릴 수
없음), `고르다`(어떤 행위인지 정할 수 없음), `마무리`(남은 일이 무엇인지 문장이 말하지
않음), 명사를 잇는 `하고`(동사 어미와 구별되지 않음).

이 목록에서 무언가를 발견하면 그것은 버그가 아니라 아직 하지 않은 일이다. 목록에
**없는** 것이 틀렸다면 그것이 버그다.
