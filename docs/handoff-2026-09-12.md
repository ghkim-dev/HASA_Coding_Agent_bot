# 인수인계 보고서 — 새 설계서를 쓰기 위한 재고 조사

작성일 2026-09-12 · 브랜치 `feat/harness-auto-design` · HEAD `14cc274`

이 문서는 **무엇이 있고, 그중 무엇이 실제로 도는가**를 코드에서 직접 확인해 적은
것이다. "함수가 있다"와 "제품이 그것을 쓴다"를 구분해서 적었다 — 그 둘을 섞어 보고한
것이 이 프로젝트의 가장 큰 실수였기 때문이다.

## 0. 요청과 결과의 대조

요청하신 방향은 이것이었다:

> 유저가 원하는 요구사항에 대해서 **VectorDB형태 테이블을 만들어서 계속해서 고도화**
> 해나가고, 이를 바탕으로 **적합한 LLM모델로 이어주는 하네스를 자동 추천 및 설계
> extension**을 개발하는게 주가 되면 될 거 같아

| # | 요청 | 상태 | 확인 방법 |
|---|---|---|---|
| ① | 요구사항 벡터 테이블 | 자료구조·시험 있음 | `requirementMemory.ts`, `requirementMemoryStore.ts` |
| ② | **계속 고도화** | **한 줄도 쌓인 적 없음** | `.arena` 에 기억 파일 자체가 없음 |
| ③ | 모델 자동 추천 | **동작함** | 확장이 `designHarness({models})` 호출 |
| ③-b | 기억 → 추천 연결 | **호출자 없음** | `remembered` 를 채우는 제품 코드 0곳 |
| ④ | extension | **설계 패널 동작** | `hasa.designHarness` 등록·호출 확인 |
| ⑤ | 모델별 역할 배정 | 스크립트만 | `scripts/roleAssign.mjs`, 제품 기능 아님 |

**②가 이 프로젝트의 빈칸이다.** 쓰기는 `previewCli --remember` 플래그 뒤에만 있고,
읽어서 추천에 넣는 경로는 어디에도 배선되어 있지 않다.

## 1. 실제로 도는 것 — 지금 제품이 하는 일

### 1.1 확장(VS Code)에서 일어나는 일

`HASA: 하네스 설계` 명령 → `designerHost.ts:121` → `designHarness({text, models})`.

```
사용자 문장
  → [규칙 추출기]  요구사항·금지·근거 구간          ← LLM 안 씀
  → [능력 수요]    coding·toolUse·webResearch …
  → [라우터]       모델 순위 + 선정 이유 + 탈락 사유  ← 모델 목록 필요
  → [청사진]       요구사항마다 검증 시나리오·오라클
  → 패널 표시 + 「코딩 에이전트로 넘기기」
```

**중요한 구조적 사실 두 개:**

1. **확장은 LLM 제안자를 쓰지 않는다.** `designerHost` 는 `propose` 를 넘기지 않으므로
   `previewDesign` 이 오프라인으로 돈다. 요구사항은 전부 규칙 추출기가 읽은 것이고,
   LLM 은 **모델 추천의 대상**일 뿐 요구사항 읽기에 관여하지 않는다.
   제안자를 쓰는 유일한 자리는 CLI(`previewCli.ts:142`)다.
2. **설계 단계는 아무것도 실행하지 않는다.** 파일도 명령도 건드리지 않으며, 이것은
   주장이 아니라 `preview.test.ts` 가 `writeFile`·`spawn` 을 바꿔치기해 확인하는 성질이다.

### 1.2 규칙 추출기가 읽는 것

| 읽는 것 | 구현 | 비고 |
|---|---|---|
| 행위 + 대상 | `functionalExtract.ts` | 동사 사전 + 조사·어미 규칙 |
| 금지 — 실행 | `statedProhibitions.ts` | 실행·돌리기·구동 + **배포·커밋·머지·푸시** |
| 금지 — 수정 | 〃 | 수정·고치기·변경·건드리기 |
| 금지 — 웹 | 〃 | 웹/인터넷 한정 |
| 금지 — **결과물** | `outputProhibitions.ts` | "제품명은 결론에 넣지 마" — 도구를 막지 않는 금지 |
| 근거 구간 | `sourceSpan.ts` | 사용자 원문의 좌표. 모델이 만든 문자열이 아님 |
| 조건·범위 | `semanticAlignment.ts` | "…라면", "src 폴더 안에서만" |

### 1.3 라우터가 하는 일

`taskProfile` 이 요구사항에서 **12개 능력 수요**를 뽑고(`coding`, `debugging`,
`reasoning`, `architecture`, `codeReview`, `toolUse`, `commandExecution`,
`webResearch`, `sourceGrounding`, `instructionFollowing`, `recovery`,
`multiTurnContinuity`), `recommend` 가 모델 프로파일과 대조해 순위·이유·탈락 사유를
만든다.

근거 등급 사다리: `declared`(1) < `benchmark`(2) < `harness_eval`(3) <
`observed`(4) < `manual`(5). **낮은 등급을 높은 척하지 않는 것**이 이 사다리의 전부다.

### 1.4 검증 청사진

요구사항마다 시나리오를 만든다. 금지는 부류마다 **다른 도구**를 막는다:

| 금지 부류 | 오라클이 막는 것 |
|---|---|
| execute | `run_command` |
| modify | `write_file`, `create_file`, `apply_patch`, `delete_file` |
| research | `web_search`, `web_fetch` |
| output | 사용자가 쓴 표현 자체 (`forbiddenOutput`) |

과다 거부를 잡는 반대편 시나리오가 항상 함께 선다 — 금지만 검증하면 **아무 일도 하지
않는 하네스가 통과**하기 때문이다.

## 2. 있는데 안 도는 것 — 배선 재고

제품 코드가 부르는지를 동적 import 까지 포함해 확인한 결과다.

| 모듈 | 제품 호출자 | 상태 |
|---|---|---|
| `requirementMemory.ts` | `previewCli`(쓰기), `memoryEvidence`, `modelProposer` | **읽기 경로 미배선** |
| `requirementMemoryStore.ts` | `previewCli` 만 | `--remember` 플래그 뒤 |
| `memoryEvidence.ts` | `modelProposer` | `remembered` 가 비어 있어 항상 no-op |
| `proposerEvidence.ts` | **없음** | 스윕 결과를 프로파일로 올리는 다리. 아무도 안 부름 |
| `previewMetrics.ts` | **없음** | 시험에서만 |

### 기억 사슬이 끊긴 자리

```
previewCli --remember  →  recordTurn  →  saveMemory  →  .arena/…json
                                                            ↓
                                                       (읽는 사람 없음)
                                                            ↓
  modelProposer.remembered  ←  ✗ 아무도 채우지 않음  ←  nearest / verdictFor
```

`demoteRemembered` 와 `memoryEvidence` 는 구현·시험·변이까지 있으나 **시험이 먹이는 것
말고는 아무것도 들어가지 않는다.** 새 설계서에서 ②를 살리려면 이 화살표를 이어야 한다.

## 3. 측정된 것 — 숫자와 그 분모

숫자는 전부 분자·분모로 적는다. **아래는 전부 "요구사항을 읽어내는 정확도"이지 업무
성공률이 아니다.** 고객 자료로 한 업무를 끝까지 돌려 본 적이 없다.

### 3.1 말뭉치와 점수

| 말뭉치 | 크기 | 점수 |
|---|---|---|
| Gold (개발셋) | 45 사례 | recall·precision·target·span 각 **65/65** |
| Holdout | 33 사례, sha256 고정 | target 43/43 · relation 38/38 |
| 산업군 12개 | 24 문장 / 요구 38 | 행위 33/38 · **대상 17/38** |
| 산업군 — 금지 | 명시적 금지 7건 | **7/7 읽어냄** |
| 산업군 — 오탐 | 금지 없는 17건 | **17/17 지어내지 않음** |
| IT·DX 컨설팅 | 25 문장 | 25/25 · 행위 33/33 · 대상 30/33 |
| 생성형 미디어 (한/영) | 31 / 25 문장 | 30/31 · 25/25 |
| 모델 추천 | 20 사례 | 20/20 |

> **24/24 로 읽지 말 것.** 금지 지표는 성질이 다른 둘이다 — 7/7 은 *읽어내는* 능력,
> 17/17 은 *지어내지 않는* 능력. 합치면 "전부 빈 목록을 내는 판독기"가 절반을 공짜로
> 얻는다.

### 3.2 측정이 무력하지 않은지 재는 장치

| 장치 | 묻는 것 | 결과 |
|---|---|---|
| 단위 시험 | 코드가 약속대로 도는가 | **5,794 / 5,794** (건너뜀 0) |
| `design:mutate` | 방어를 빼면 시험이 알아채는가 | **314 / 314**, 예상 밖 무반응 0 |
| `design:answers` | 정답을 바꾸면 시험이 빨개지는가 | **961 / 969**, 예상 밖 0 |
| `audit:assertions` | 단언을 한 번도 실행 안 하는 시험 블록 | 3,567 중 17(전부 분류됨) |

이 셋이 이 프로젝트에서 **가장 재사용 가치가 높은 자산**이다. 테스트가 통과한다는
것과 테스트가 무언가를 검사한다는 것은 다르고, 그 차이를 재는 장치는 만들어 두면
어느 설계에서나 쓴다.

### 3.3 LLM 성능 실측 (게이트웨이 4모델 · 10사례)

**근거를 좌표로 받을 것인가 인용으로 받을 것인가** — `scripts/quoteVsOffset.mjs`

| 형식 | pointed | named |
|---|---|---|
| 좌표만 (예전) | 10/64 | 40/64 |
| 인용만 | 33/64 | 31/64 |
| **둘 다 (현재 배송)** | 32/64 | 34/64 |

- `ax-3.1`·`qwen2.5-coder-32b` 는 좌표를 **0%** 맞춘다. 과제를 못 하는 게 아니라 **글자를
  못 센다** — 인용으로는 56%·69%.
- `exaone-4.0-32b` 은 **반대로** 인용만 요구하면 빈 배열을 낸다.
- 그래서 둘 다 요구하고 런타임이 확인된 쪽을 쓴다. 배송 프롬프트 재측정: `ax-3.1`
  0%→44%, exaone 19%→25%, gpt-oss-20b 유지.
- **일반화하지 말 것:** 한 게이트웨이, 네 모델, 열 사례, 세 번의 실행이다. 온도 0인데도
  실행마다 값이 다르다(A팔 12/64 vs 10/64).

**출력 예산** — `scripts/budgetFloor.mjs`

| 모델 | 800 | 4800 |
|---|---|---|
| exaone-4.0-32b | 3.8s 답 | 4.7s 답 |
| gpt-oss-20b | 2.7s **빈 답** | 9.2s 답 |
| gpt-oss-120b | 3.8s **빈 답** | 4.9s 답 |
| ax-3.1 | 1.7s 답 | 2.0s 답 |

빈 답 둘은 `finish_reason: "length"` — 예산이 끊은 것이지 모델이 못 한 것이 아니다.
현재 `MAX_OUTPUT_TOKENS = 4800`. 관측된 바닥이지 증명된 문턱은 아니다.

### 3.4 외부 데이터로 잰 한계 — KLUE-DP 2,000문장

목적어 명사구 1,691개, 사람이 붙인 의존 트리.

| 목적어 경계 규칙 | 정확 | 잘림 | 과잉 |
|---|---|---|---|
| 고정 1어절 | 39.1% | 60.9% | 0.0% |
| **고정 2어절 (현재)** | **27.6%** | 36.4% | 36.0% |
| 고정 3어절 | 18.6% | 23.9% | 57.5% |
| 품사 태그로 경계 찾기 | 69.4% | 22.0% | 8.6% |
| 표면형만으로 | 47.1% | 18.7% | 34.1% |

- 목적어구는 **100% 연속**이고 3어절 이상이 36%다.
- **폭을 바꿔서 될 일이 아니다** — 어느 값이든 양쪽으로 함께 틀린다.
- 69.4% 는 **정답 태그를 읽은 오라클 상한**이지 도달 가능한 값이 아니다. 형태소
  분석기를 넣으면 47.1% 와 69.4% 사이 어딘가이고, 어디인지는 재 봐야 안다.

## 4. 알려진 결함 — 새 설계서가 상속할 것

### 4.1 산업군 말뭉치 미해결 (`INDUSTRY_GAPS`)

| 원인 | 건수 | 설명 |
|---|---|---|
| 목적어 앞머리 잘림 | 20 | "행정 정보 시스템의 접근 권한 모델" → "권한 모델" |
| `정리하다` 의 두 뜻 | 4 | 기술 부채를 정리(수정) vs 탐지 룰을 정리(읽고 답함) |
| 목적어 없는 둘째 절 | 1 | "재현하고 **고쳐줘**" 의 뒤 절이 사라짐 |

### 4.2 재지 않은 축 (`UNMEASURED`)

- `priority`(must/should/may), `kind`(functional/…) — 정답을 기록하지 않음
- span **최소성** — 포함만 확인, 최소 구간인지는 안 봄
- **모델 제안의 recall/precision** — Gold 는 오프라인 추출기만 대상
- 다중 턴 요구사항 승계 — merge 후 남아야 할 집합의 정답 없음

### 4.3 일부러 읽지 않는 것

`쓰다`(쓰기/사용하기 구분 불가), `고르다`(행위 미정), `마무리`(남은 일이 문장에 없음),
명사를 잇는 `하고`, 조사 없는 `봐줘`("이거 봐줘").

### 4.4 구조적으로 남은 위험

| 위험 | 현황 |
|---|---|
| 설계→Agent 계약 | `harnessHandoff` 는 원문과 모델만 넘긴다. 승인 조건이 실행 뒤 보존되는지 추적 없음 |
| 고객별 저장 격리 | `saveMemory` 는 읽기→병합→쓰기. 동시성 조정 없음 |
| 기억 결과 라벨 | `accepted` 가 "사용자 확인"과 "그냥 안 고쳐짐"을 구분 못 함 |
| 온프레미스 경계 | Base URL 만 바꾼다고 내부로 닫히지 않음. 임베딩·OCR·미디어·업데이트 경로 미정리 |

## 7. 이 프로젝트가 실패한 지점 — 새 설계서가 피해야 할 것

세 가지를 솔직하게 적는다.

**하나. 잴 수 있는 것을 골랐다.** 형태소 규칙은 2,000문장으로 재고 변이로 검증할 수
있다. "기억이 쌓여서 추천이 나아진다"는 며칠의 실사용이 있어야 재진다. 매번 잴 수 있는
쪽을 골랐고, 그건 편의였지 요구가 아니었다. → **새 설계서는 완성 조건을 먼저 문장으로
못 박고, 잴 수 없는 것도 그 조건에 넣어야 한다.**

**둘. 검수에서 나오지 못했다.** "제품으로 돌아가서 완성품부터"라는 지시를 두 번 받고도
측정으로 돌아갔다. → **검수·측정은 요청이 있을 때만.**

**셋. 배선 안 된 것을 배선된 것처럼 보고했다.** "기억이 추천을 움직인다"고 적었고
사실이 아니었다. 외부 검토가 짚어 준 뒤에야 확인했다. → **보고서에서 "함수가 있다"와
"제품이 쓴다"를 구조적으로 분리.** 이 문서의 2장이 그 형식이다.
